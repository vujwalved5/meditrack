### 2.3 Discovery Questions & Answers
1. **Status model:**
   - Database schema: `equipment.status` has CHECK (`Available`, `In Use`). `equipment.condition` has CHECK (`Usable`, `Needs Maintenance`, `Out of Order`).
   - UI previously only checked `status` (`Available` vs `In Use`) and ignored `condition` in filters/KPIs. The AI brief referenced non-usable equipment via `condition !== 'Usable'`.
2. **How is "Utilization" computed:**
   - In `daily-insights/metrics.ts`: Yesterday's 24-hour window (Asia/Kolkata).
   - Formula: `(totalInUseHours / (nonOutOfOrder.length * 24)) * 100`.
   - `1.7%` represents 25 total equipment-hours used out of `61 * 24 = 1464` available equipment-hours yesterday. It is yesterday's utilization rate, distinct from current instantaneous in-use count (22).
3. **How is "overnight" defined:**
   - Equipment currently `In Use` with `in_use_since` before today's 00:00:00 (Asia/Kolkata). All 22 in-use items met this in seed data.
   - "5 held over 47 hours" was generated by LLM from an ungrounded inference or checkout dates in audit history; not from a dedicated field.
4. **How is "Forgotten Equipment" decided:**
   - In `daily-insights/metrics.ts`: `heldHours >= Math.max(medianHours * 3, 24)`.
   - Infusion Pump had median duration ~3.8h, so threshold was 24h. Infusion Pump A was held 43h 30m (11.4× median), exceeding threshold. Other equipment types either had higher thresholds or insufficient history, so only 1 item was flagged.
5. **Product-type tiles:**
   - `buildEffectiveTiles()` queried `product_types` table.
   - In `migration_v3.sql`, only `Ventilator A` and `Ventilator B` had `product_type_id = 1` set. Ventilator C and D had `NULL`. Filtering by `eq.product_type_id === pt.id` resulted in 2 items instead of 4. Other equipment types lacked rows in `product_types`.
6. **User model & capabilities:**
   - `users` table: `id, username, password_hash, role, department_id, is_active, created_at`. No `last_login` column.
   - No update endpoint for user role/department; no notification table or endpoint; no equipment transfer endpoint.
7. **What drives the LIVE pill:**
   - Supabase Realtime WebSocket subscriptions exist in `subscribeRealtime()`, but the `#live-badge` DOM element was hard-coded static markup.
8. **Date in Operations Brief:**
   - "October 4, 2026" was the date covered (yesterday's data), while "Generated 05 Oct" was the execution date. The brief lacked explicit "Covers 4 Oct 2026" labeling, appearing as a contradiction.

## Assumptions Made
1. **Product Type Grouping:** Since `migration_v3.sql` only populated `product_type_id = 1` for two Ventilators and left others null, client-side grouping parses base product names from equipment names (e.g. "Ventilator A" -> "Ventilator") so that all 61 items are visible and navigable without mutating database rows.
2. **Weekly Date Range Display:** When week boundary dates are present, they are formatted as `26 Sep – 2 Oct 2026` instead of raw ISO timestamps.
3. **Audit Log Default Order:** Default sort orders rows by `last_activity` descending, placing equipment with 0 recorded uses at the bottom as specified in P1-12.
4. **Destructive Action Confirmations:** Confirm dialog for user deactivation defaults focus to the "Cancel" button to prevent accidental clicks.
